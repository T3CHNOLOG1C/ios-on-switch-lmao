Current status, 2026-10-29: **V24 raw APFS installer and boot entries are staged, verified and safely ejected.** Android is erased only by the on-device installer confirmation. The eight 2 GiB FAT-backed Data files remain for V19 recovery; they are not recopied or content-hashed. The new raw candidate contains complete original Data, including staged apps, in a shared 32 GiB container. [Raw installation procedure](native-raw-apfs.md). The earlier V23 installation retained these FAT files. [V23 receipt](../out/switch/native-xnu-v23-install.json), [audit and fixes](native-audit.md). The original Data installation passed full host readback. V17 subsequently reached native daemon execution with repeated relaunches and a photographed APFS flush; successful complete startup, reboot persistence and the iPadOS UI remain unverified.

The prepared image has a real 16 GiB APFS container: 4,194,304 blocks of 4,096 bytes, with no volume quota. It preserves container UUID `FF7FE547-2663-4CFD-9EAD-E458573AE97C` and Data volume UUID `CCD5A1A2-2FDC-4B25-B322-AE1722871BC9`. The eight fully materialized FAT32 files `/IOSWITCH/WRITABLE/DATA0000.BIN` through `DATA0007.BIN` are each exactly 2 GiB and concatenate in filename order. Their 8.3 names work with the existing FAT parser. Preparation checked all 206 retained inode metadata rows and compared every newly created part byte with its source chunk. It did not hash the old seed or all logical Data contents.

The initial seed includes `/private/var` **except `/private/var/staged_system_apps`**. Expanding APFS does not restore that omitted subtree or prove application readiness. Native boot must preserve the existing Data bytes; it does not recreate the seed or initialize Data on each boot. The old RAM Data provider returns before claiming its seed when `ioswitch-root-boot=1`. Its inert seed sidecar remains in the adapter layout only to keep that handoff contract unchanged.

Copying the installation to another compatible FAT32 SD card, or moving the files to different clusters, does not require rebuilding the kernel. Partition discovery validates GPT or the four primary MBR entries, then chooses the unique FAT32 partition containing the required image paths and sizes. It does not assume a partition GUID, position or order. The filesystem must be GPT Basic Data or primary MBR FAT32 (type 0x0B/0x0C); extended/logical MBR, superfloppy, FAT16 and exFAT are not supported. The existing SD transport requires 512-byte sectors and SDHC/SDXC block addressing up to 2 TiB. Card capacity and protocol identity come from the current boot. These are format and transport limits, not installation-specific bindings.

The three native disks share one controller owner and one sleepable lock. OS and SystemOS remain read-only; only the typed persistent Data child accepts writes. Each request is limited to 64 KiB, and the complete client buffer is copied to private staging before any write. The Data backend finds the eight files and builds their allocation map from the current FAT filesystem at each boot. It checks their sizes, distinct clusters, disjointness from OS/SystemOS files, and complete ancestor directory chains before permitting writes. Every write stays within that runtime map; no card identity, partition GUID or sector table is compiled in. The transport separately requires an exact-range permission callback before any register I/O. Native XNU never allocates or extends the host files, updates FAT entries, directory entries or FSInfo, or exposes erase, format or unmap. Host installation creates the files through the host filesystem; these restrictions describe the subsequent native path.

The SD transport qualifies the card using CMD13, SCR and, where advertised, bounded CMD48 extension reads. It permits writes only when the optional write cache is unsupported or observed disabled; enabled or unknown cache state is refused. Current CMD24/CMD25 writes use required 64-bit SDMA with a private contiguous buffer and cache maintenance, plus Auto CMD12 for multiple blocks, then require idle DAT0 and CMD13 `READY_FOR_DATA` in transfer state. Synchronize takes the same owner lock and performs that card-ready barrier after earlier writes. This is not a guarantee that an entire multi-sector write is atomic under power loss. A failed operation may have changed a prefix; the shared owner goes offline without an automatic retry or rollback claim.

The mount path selects the preserved Data UUID only under the persistent provider, rechecks the actual APFS device and 16 GiB capacity, and requires a writable mount with ownership enabled, root-owned Data root and UID/GID 501 for `mobile`. Mutable Data cannot authorize an OS root. The watchdog policy accepts an already valid policy/marker pair, creates missing files, syncs policy before marker and syncs parent directories. V18 preserves an existing root-owned, same-mount, non-symlink regular policy without group/other write permission, allowing original launchd to parse and rewrite its own preferences. It creates only a missing initial policy through an exclusive atomic rename after readback and fsync; policy and directory syncing precede marker creation. Publication pending yields for at most ten seconds; corruption, wrong identity and offline errors remain immediate failures.

The active implementation is under `out/native-a57/root-v1/tree/`; the older canonical `native/storage/` files are not the current V17 implementation.

For the retained FAT fallback, physical persistence still requires a native boot with these portable Data files. V23 subsequently reported a root-device discovery failure, and the owner requested the separate raw profile. The first native boot must mount Data and complete writes and synchronize without disk errors. A second boot must observe the previously written Data with the same UUID and capacity, without reseeding or reinitialization. Until those observations are recorded, host preparation, source review and fault-injection tests remain separate from installation, native write success, reboot persistence and UI readiness.
