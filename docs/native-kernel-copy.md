# Native kernel-copy performance

The V14 loader copies 70,303,744 bytes (67.05 MiB) from its staging buffer into XNU's owned window. The copy runs with the MMU, instruction cache and data cache disabled. Its emitted loop performs one eight-byte load and store per iteration: 8,787,968 iterations. Under the inherited Arm configuration, those data accesses use Device-nGnRnE attributes. This is the leading explanation for the slow copy, based on source and disassembly; the time distribution has not been measured on the Switch.

The kernel CRC passes were already removed in V13. Progress text adds about 0.88 MiB of framebuffer stores across the copy, while the copy itself makes about 17.58 million data accesses. Reducing progress redraws alone is unlikely to address the main cost. The on-screen millisecond counter includes the copy and progress work.

V17 implements a temporary identity mapping with normal cacheable RAM for the loader, source and destination, while leaving the framebuffer as device memory. The existing memory-ownership checks run before the first destination write. An integer loop copies 64 bytes per iteration, then cleans dirty data to the point of coherency and restores the incoming translation and cache state before XNU entry. The code requires the A57 coherency setting to be present; it does not alter that CPU control.

Seven 4 KiB translation tables and a 48 KiB main stack fit within the 112 KiB loader, below the separate SD reference page. The final cache-clean sequence makes no calls, stack accesses or stores before disabling the temporary mapping. Failure prevents kernel entry. Source, emitted instructions, layout and stack usage passed an independent review; focused host table checks covered 32 complete descriptor walks and 21 malformed inputs with guard pages and ASan/UBSan.
