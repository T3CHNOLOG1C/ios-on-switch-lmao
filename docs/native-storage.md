## V4 same-boot comparison

After U-Boot prepares the native handoff, the boot script reads explicitly from whole-device `mmc 1`, sector zero, count one. It stores the 512 bytes and CRC in a fixed 4096-byte page at `0xA001F000`, within the existing excluded adapter reservation. Every adapter segment and stack ends before this page. The loader checks the page against live memory reservations, validates all metadata, reserved bytes and CRC, then commits it only after verifying the copied kernel and boot arguments. The firmware read can use U-Boot's block cache; it is a reference for comparison, not evidence of XNU storage access.

After the signed PID 1 completes its three real system calls, XNU maps the reference read-only, validates its commit and exact `/chosen` pointer, and maps SDMMC1 at `0x700B0000` as Device memory. MMIO callbacks limit accesses to the controller's first `0x200` bytes. The mapping granularity is 4096 bytes; callbacks never access the eMMC controller at offset `0x600`. A one-CPU gate and interrupt masking serialize the single polling attempt. The only permitted command is CMD17 for sector zero; no filesystem, general block-device service, recovery or retry is provided.

Success requires all 128 FIFO words, completed transfer, idle controller, matching CRC and all 512 bytes matching the firmware reference. Only then does the screen show **`SD SECTOR 0 MATCHES U-BOOT - READ ONLY`**. A failure or mismatch instead shows the transport stage, error/status, read count, inherited registers and CRCs. See the [run guide](native-xnu-run.md). The owner has now reported this result. It establishes one native sector read; a partition mount and iPadOS boot remain unfinished.

## Which controller belongs to the removable card

The source [Switch control tree](../out/research-native/switch-uboot/arch/arm/dts/tegra210-nintendo-switch.dts) maps U-Boot `mmc1` to SDMMC1 at `0x700B0000`; `mmc0` is the internal eMMC controller at `0x700B0600`. The SD node has a four-bit bus, card-detect GPIO Z1 active low and power GPIO E4. The captured [live OLED Linux tree](../out/switch/native-live-hardware.json) independently describes SDMMC1 at `0x700B0000`, register extent `0x200`, four-bit bus and interrupt cells `(0,14,4)`, which identify GIC interrupt 46. The planned polling transport does not enable that interrupt or use DMA/IOMMU mappings.

Card presence is checked through GPIO by U-Boot's `tegra_mmc_getcd`. The standard SDHCI present/stable bits may therefore refuse a valid inherited controller state on this board. The portable module intentionally refuses when those bits are absent; a hardware observation is needed before changing that gate.

## Evidence that firmware leaves a selected card

The audited source is Switchroot U-Boot revision `722e2b86be9ab1ae073335585c5997093e05f4f2`. It is the existing firmware's source reference, **not** a reproduced build of the installed BL33. Source evidence supports the following candidate contract; the final adapter must still check runtime state.

| Source | Relevant behavior |
| --- | --- |
| [MMC core](../out/research-native/switch-uboot/drivers/mmc/mmc.c), `mmc_startup` | CMD7 selects the initialized card into transfer mode. |
| Same source, `mmc_bread` and `mmc_read_blocks` | Reads establish `read_bl_len`, use CMD17 for one block or CMD18 followed by CMD12 for multiple blocks, and do not deselect the card afterward. |
| [ARM boot handoff](../out/research-native/switch-uboot/arch/arm/lib/bootm.c), `announce_and_cleanup` | Calls the board quiesce hook, flagged device removal and CPU cleanup. The Tegra board has no override of the empty quiesce hook. |
| [Device removal](../out/research-native/switch-uboot/drivers/core/device-remove.c) and [Tegra MMC driver](../out/research-native/switch-uboot/drivers/mmc/tegra_mmc.c) | Boot removal invokes flagged driver callbacks. `tegra_mmc_drv` has neither a removal callback nor an active-DMA/OS-preparation flag. |
| [Tegra board cleanup](../out/research-native/switch-uboot/arch/arm/mach-tegra/board2.c) and [UPHY cleanup](../out/research-native/switch-uboot/arch/arm/mach-tegra/tegra210/xusb-padctl.c) | Tears down USB/UPHY; this path does not reset SDMMC1, deselect its card or disable its clock/power. |
| [ARM64 CPU cleanup](../out/research-native/switch-uboot/arch/arm/cpu/armv8/cpu.c) | Disables interrupts, caches and the MMU; it does not reinitialize MMC. |

No native adapter may call a U-Boot function after this handoff. The proposed driver reuses the hardware state, not firmware code or firmware-owned pointers. The controller must be mapped as Device memory with an independently validated address, and one owner must serialize every access.

## Addressing is a separate requirement

The MMC core sets `high_capacity` from the card's OCR bit 30. It sends sector numbers for SDHC/SDXC cards and byte addresses for ordinary SD cards. Card capacity inferred from a host disk listing, a partition table or a product label does not establish this protocol state.

The pinned [`mmc info` command](../out/research-native/switch-uboot/cmd/mmc.c) prints `High Capacity: Yes/No` from that real field. Its optional argument exports only the manufacturer ID; it cannot export an OCR or high-capacity flag to a boot-script variable. The same source's `mmc dev` command forces reinitialization even when used without arguments, so it is not a read-only inherited-state query.

Until a same-boot firmware record or an independently qualified protocol check establishes addressing, the transport permits **only CMD17 argument zero**, with a one-sector allowed range. Byte address zero and sector zero are identical. It also requires an inherited 512-byte block-size register; the board contract must retain the preceding successful firmware read with that block length. This mode is only a sector-zero probe, not a capacity claim.

## Bounded PIO contract

The register layout and command bits are checked against [Tegra MMC declarations](../out/research-native/switch-uboot/arch/arm/include/asm/arch-tegra/tegra_mmc.h). The PIO sequence is independently present in the [generic SDHCI implementation](../out/research-native/switch-uboot/drivers/mmc/sdhci.c). The Tegra U-Boot driver itself uses DMA; the new native transport uses PIO and supplies no DMA address.

Before any write, the module requires reviewed SDHCI 3.0 or 4.0, a present and stable card, inherited four-bit mode, power and stable enabled clocks, a 512-byte block size, no software reset, no command/data inhibit or active transfer, and no existing error status. It masks interrupt signals, enables the required status events and defined error bits, clears only its completion events, then issues command `0x113A` with transfer mode `0x12`: CMD17, R1 response, CRC and command-index checks, one 512-byte read, no automatic command and no DMA.

Each completion wait has a one-second counter deadline and a one-million-iteration fallback. Errors take precedence when completion and error bits appear together. The reader checks the card's R1 errors, waits for buffer-ready status and the present-state data-available bit, reads exactly 128 32-bit FIFO words into a private temporary buffer, and waits for transfer completion and an idle controller. Only then does it copy 512 bytes to the caller and restore the temporary control-register settings.

The module never writes a power, clock, tuning, GPIO, reset or DMA-address register, and it issues no media-write or erase command. A failed command leaves signal interrupts masked, marks the host blocked for the rest of the boot and preserves the caller's output. It does not attempt a reset, retry, card reinitialization or recovery that could hide an incomplete transfer.

## Historical transport-only next steps

The owner-reported v6 result completes the first sector-zero comparison. Future runs can add photographic evidence and exact register values. Record the inherited host registers, command response, completion/error status, word count and final idle state. Stop immediately on a gate failure or transport error; neither a readable controller version nor a plausible MBR signature is sufficient evidence by itself.

Next, establish card addressing and actual capacity, then constrain reads to a separately validated partition. A FAT reader needs its own bounds checks for the boot sector, sectors per cluster, FAT copies, cluster chains, partition extent and a finite traversal budget. A successful file read should match an existing host digest. An XNU `IOBlockStorageDevice` integration and filesystem mount remain additional work; the current transport and RAM-disk experiment do not provide them.
